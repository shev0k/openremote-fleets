Use mock mode for quick UI work. Use the emulator when you need Manager-created assets, real datapoint history, route playback from Manager, or real-mode fallback behavior.

The emulator does not emit Fleets-only marker objects. Fleets still derives stop, idle, break, signal, engine-off, and offline markers from history.

## Run it

From Windows PowerShell:

```powershell
cd teltonika-emulator
.\run.ps1
```

From macOS or Linux:

```bash
cd teltonika-emulator
python3 run.py
```

The launcher creates `.venv`, installs dependencies when needed, starts FastAPI, opens the browser, and uses port `8090` or the next free port.

Useful flags:

```bash
python run.py --no-open
python run.py --no-autostart
python run.py --port 8095
python run.py --reinstall
```

If `config/emulator.local.yaml` is missing, the emulator starts from built-in demo trackers. Saving from the UI writes that ignored local config file.

## Manager setup

For the normal TCP path, start the local Teltonika-enabled Manager from the repository root:

```powershell
.\scripts\run-openremote-manager-local.ps1
```

Then check Manager:

1. Manager is available at `https://localhost/manager`.
2. A Teltonika agent exists.
3. The agent transport is `TCP` or `BOTH`.
4. The agent bind port is `5027`.
5. The emulator config points to `127.0.0.1:5027`.
6. One or more trackers are running from the emulator UI.
7. Fleets is running in real mode with `npm run dev`.

Manager should create one `TeltonikaTrackerAsset` for each emulator IMEI. Fleets real mode queries those assets through the normal OpenRemote repositories.

## TCP and MQTT

TCP is the main path. The emulator identifies with IMEI, waits for Manager's accept byte, sends Codec 8 AVL packets, and reads the accepted-record ACK.

MQTT is a fallback. It publishes OpenRemote Teltonika JSON to:

```text
{realm}/{client_id}/teltonika/{imei}/data
```

MQTT sends raw Teltonika values. For example, `3.812 V` battery voltage becomes `3812`, and `0.8` HDOP becomes `8`.

## Data contract

The emulator emits the Fleets-supported Teltonika subset: position, heading, satellites, speed, ignition, movement, optional `trip`, GSM, GNSS, power, battery, odometer, fuel, sleep/data mode, engine RPM, and `iButton`.

The same attribute names are documented in `src/domain/models/teltonikaCatalog.ts` and `docs/03-live-fleets/04-teltonika-openremote-data.md`.

Keep these rules in place:

- tracker identity is a 15-digit IMEI
- `gpsLocation` is preferred, Manager `location` is still a valid fallback
- missing telemetry stays missing
- poor GNSS or GSM is degraded signal, not automatically offline
- `iButton` is a device/driver identifier, not a human name
- `driverName`, `plate`, and `assetClass` are optional Manager text attributes, not Codec 8 fields

## Manager history sync

Route playback and charts need Manager datapoint storage. The emulator can enable this automatically after Manager creates the tracker asset.

It logs in to Manager, finds the `TeltonikaTrackerAsset` by IMEI, renames it to the emulator tracker name, and sets `storeDataPoints: true` on the useful telemetry attributes.

Default local API settings:

```yaml
manager:
  api:
    enabled: true
    base_url: https://localhost
    realm: master
    client_id: openremote
    username: admin
    password: secret
    verify_tls: false
    auto_store_datapoints: true
```

This only affects new datapoints. Manager cannot backfill history for packets that arrived before datapoint storage was enabled.

## Verification

Run emulator tests from `teltonika-emulator/`:

```bash
python -m pytest
```

The suite checks Codec 8 framing and CRC, TCP handshake, MQTT payload scaling, route simulation, Manager history setup, web API behavior, and alignment with Fleets mock fixture values.

After Storybook docs changes, also run:

```bash
npm run build:storybook
```
